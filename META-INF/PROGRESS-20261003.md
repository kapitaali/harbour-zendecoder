### Architecture decision (daemon vs static link)
- v0.1 decodes via system `org.amberapi.zxing` D-Bus daemon (text only,
  `format` reserved empty). Rationale: SDK target ships zxing-cpp **2.0.0**
  headers while the 5.2 device runs **3.0.2** (`libZXing.so.3`) — linking
  the system lib would bake the wrong soname; vendored static zxing-cpp
  (PLAN.md plan B) is the correct full-format path and lands next.
- Daemon introspection: only `decodeFromDescriptor` + `quit` (strings on
  `/usr/libexec/zxing-daemon`); wraps `ZXing::ReadBarcode` + `ReaderOptions`.
  No format-returning method exists.

### Do-not-re-derive (from sailauth, applies here)
- VideoOutput `filters` do NOT run on device (overlay backend, Qt 5.6 `qdeclarativevideooutput_window.cpp` has no filter chain). `QVideoProbe::setSource` fails. Use still captures keyed off `imageSaved` (preview signal `imageCaptured` never fires; only file captures guaranteed).
- Full-res stills are 8192x6144 (~3s cycle, ~200MB as ARGB32): negotiate capture resolution down (sailauth ceiling 1920x1440; 2560 kills camerabin). Private cache file, delete after decode.
- Daemon wants tightly packed `Format_ARGB32` (`kPixelFormat=1`); other formats return empty (probe-verified on device).
- `sfdk build` compiles in place: arch-switch needs `rm -f Makefile .qmake.stash *.o moc_*.cpp <binary>` first (never `git clean -xdf`, kills `RPMS/`). Each target -> own `RPMS/<target>/` subdir.
- Spec carries no `%changelog` (sfdk generates via `rpm/*.changes.run` into `.sfdk/spec`); RPM version comes from git tag (dirty tree = `0.x+main...` suffix the validator rejects — tag first).
